## 0. 结论摘要

| 项 | 决定 |
|---|---|
| 实现语言 | **C++20**（单一 CMake 工程） |
| GUI 框架 | **Qt 6 Widgets**（原生控件，非 QML、非 WebView） |
| 表达式运行时 | **Lua 5.4**（PUC Lua，源码内置构建；**不用 LuaJIT**） |
| Lua 绑定 | **sol2**（header-only, MIT） |
| 架构分层 | `batchsmith_core`（静态库）＋ `bs`（CLI）＋ `batchsmith`（GUI），**逻辑零重复** |
| 代码编辑器 | **QPlainTextEdit + QSyntaxHighlighter + QCompleter**（零额外依赖）；进阶模式可选 QScintilla |
| 表格控件 | **QTableView + QAbstractTableModel**（原生虚拟滚动，免费） |
| 核心库依赖 | `core` 只依赖 **QtCore**（不用 QtGui / QtWidgets） |
| 预设格式 | **TOML**，路径为运行时槽位，不含绝对路径 |
| 执行模型 | **计划／执行两阶段**，`QProcess` 传 argv 数组不经 shell，默认 dry-run，JSONL 撤销日志 |
| 沙箱 | `_ENV` 白名单 ＋ 指令数钩子 ＋ 内存上限 ＋ 墙钟超时，**四项齐备** |
| 首版范围 | 只做最小闭环：**加载预设 → 选文件夹 → dry-run diff → 执行** |

三处对构想书/评估的改动：**取消双引擎分级**（ADR-5）、**编辑器不引入 Monaco**（ADR-4，现在连"换一个 Web 编辑器"都不需要了）、**核心沿用 QtCore 而非纯 std**（ADR-9）。

## 1. 需求与约束基线

### 1.1 功能基线（来自构想书，不再改动）

- 输入为多个一维字符串列表 ＋ 一个输出表达式；表达式可用 `$...$` 区段插入 Lua。
- 列表来源：手输 / 表达式生成 / 绑定文件夹（动态）/ 快照读取文件夹 / 生成器（seq、随机、正则捕获）。
- 列表可排序、可批量操作、可增删；多列表可锁定同步滚动。
- 逐行对齐，行数取最长；每个列表可配自己的缺省方式（Empty / Ignore / Repeat）。
- 输出可作纯文本、可作命令执行（重命名、批处理、组合命名、统计）。
- 普通模式用自定义 DSL（一行内可读）；高级模式为完整 Lua 编辑框。
- 执行方式：逐行 / 并发 / 输出脚本 / 快捷复制，并带执行日志框。

### 1.2 硬约束

| 约束 | 含义 | 对方案的直接要求 |
|---|---|---|
| **多平台** | Windows / macOS / Linux 三端可用 | 不依赖目标机预装运行时；有成熟的部署工具链 |
| **轻量化** | 启动快、体积可接受、依赖少 | 拒绝 Electron/Chromium；不使用重型第三方 UI 与编辑器 |
| **原生控件** | 界面须为类 native 控件，非 WebView | **排除 Tauri / Electron / Wails 等一切 WebView 外壳** |
| **安全** | 执行不可逆、预设可分享 | 沙箱能终止死循环与内存炸弹；执行路径不经 shell 字符串 |

用户偏好 native 控件这一条，恰好与构想书原有的「不手写编辑器与表格控件」原则**不冲突**——原因是 Qt 自己就提供了这两样（见 §2 ADR-3 / ADR-4），而在 WebView 里它们必须外部引入。

### 1.3 被排除的方案

| 方案 | 排除理由 |
|---|---|
| Tauri / Electron / Wails | 违背「原生控件」硬约束（WebView 本质是浏览器） |
| Electron ＋ Fengari | 除上述外还打包 Chromium，安装包 ≥80MB |
| Python ＋ PySide6 | 分发依赖解释器，PyInstaller 产物 40MB+ 且启动慢 |
| Java ＋ JavaFX | jlink 最小运行时仍 ~35MB，无收益 |
| Go ＋ gopher-lua | gopher-lua **无指令数钩子、无内存硬上限**，沙箱达不到硬约束 |
| C# ＋ Avalonia | 需 .NET 运行时（自包含 ~60MB） |
| Rust ＋ egui / iced | 原生、体积可控，但**代码编辑器要自己写**（无等价于 QSyntaxHighlighter 的现成件），与「不手写编辑器」原则相悖。列为 ADR-1 的备选保留 |
| Qt Quick / QML | 见 ADR-3，非能力问题而是取向问题 |

## 2. 关键技术决策（ADR）

### ADR-1 实现语言：C++20 ＋ Qt 6

**决定**：全项目 C++20；构建系统 CMake；Lua 通过 sol2 绑定。

**⚠ 先纠正 r1 的一处错误论证。** r1 把「`mlua` 的沙箱原语正好匹配需求」当作选 Rust 的核心理由。**这个理由在 C++ 上不成立。** PUC Lua 的 C API 提供完全等价的能力：

| 能力 | mlua (Rust) | PUC Lua C API (C++) | 等价？ |
|---|---|---|---|
| 能力白名单 | `set_environment` | `lua_setupvalue(L, -2, 1)` 设自定义 `_ENV` | ✅ |
| 指令数钩子 | `HookTriggers::every_nth_instruction` | `lua_sethook(L, h, LUA_MASKCOUNT, N)` | ✅ |
| 内存上限 | `Lua::set_memory_limit` | `lua_setallocf` 自定义分配器 + 计数 | ✅ |
| 墙钟超时 | 同一个钩子回调里 `Instant::elapsed()` | 同上，`std::chrono::steady_clock` | ✅ |
| 钩子由宿主安装，无需 `debug` 库 | 是 | 是 | ✅ |

**结论：沙箱能力对两种语言完全相同，不构成选型依据。** 真正的差异只在工程侧：

| 维度 | Rust | C++20 + Qt |
|---|---|---|
| 学习成本 | 新增 | **0（用户现有栈）** |
| 构建/依赖管理 | Cargo 最省心 | CMake + FetchContent 可接受 |
| GUI 层工作量 | 需引入外部控件体系 | **Qt 原生提供表格与编辑器** |
| Windows Unicode 路径/进程 | 需自己处理 `CreateProcessW` / `u16string` | **`QDir`/`QFileInfo`/`QProcess` 已踩平** |
| 三平台一致性 | 好 | 好（Qt 的本职） |
| 产物体积 | 更小 | 更大（见 §5） |

**决定理由**：GUI 是本项目工作量的大头，而 Qt 在这个项目的具体控件需求上给的比 Rust 生态多；再加上学习成本为 0、Unicode 路径这一构想书明确列为风险的项由 Qt 免费解决。体积代价被接受（§5 给实数）。

**保留的备选**：若日后发现 Qt 体积不可接受，`core` 若坚持不依赖 QtGui/QtWidgets（见 ADR-9），迁移到 Rust+egui 的路径仍然开放。

### ADR-2 分层：core 库 ＋ CLI ＋ GUI

**决定**：

```
batchsmith_core   ← 静态库：列表模型、DSL 编译器、沙箱、计划生成、预设读写、执行器
      ↑                    ↑
   bs (CLI)          batchsmith (GUI, Qt Widgets)
```

- `core` 不引用 QtWidgets/QtGui，只依赖 **QtCore**（ADR-9）。
- `core` 对文件系统与进程的访问经 `IFsProbe` / `ICommandRunner` 接口抽象 → dry-run、单测、GUI 预览共用同一条管线。
- **CLI 先行**：它是自动化可复用的形态，也是「一周内是否每天在用」这一判断门槛最省成本的验证载体。
- GUI 只做外壳，**不重写任何逻辑**——避免两套语义漂移。

### ADR-3 GUI 框架：Qt 6 **Widgets**，不用 Qt Quick

**决定**：Qt 6 Widgets + CMake。QML/Qt Quick 排除。

**理由**（依据 Qt 官方 UI 技术对比表）：

| 维度 | Qt Quick | Qt Widgets | 本项目取向 |
|---|---|---|---|
| 官方定位 | 动态、流畅、**触屏**优先 | **复杂桌面应用** | 本项目是密集数据型桌面工具 |
| 成熟桌面控件 | 需自行组合 | **二十年积累的完整集合** | ✔ |
| Model/View | 有 TableView（delegate 虚拟化） | **QTableView/QTreeView 完整 MVC** | ✔ |
| 渲染 | GPU（场景图） | CPU 软件渲染 | 数据表场景 CPU 足够 |
| 内存/启动 | 较高（需加载 QML 引擎） | **较低、启动更快** | ✔ |
| 文本编辑器 | TextArea 需经 `QQuickTextDocument` 挂 highlighter，绕 | **QPlainTextEdit/QTextEdit 原生支持** | ✔ |
| 语言 | QML + JS | 纯 C++ | ✔ 与 ADR-1 一致 |
| 动画/特效 | 强 | 弱 | 本项目不需要 |

本项目**没有一条需求落在 Qt Quick 的强项上**（无动画、无触屏、无 3D），而它的弱项（密集表格、文本编辑器、纯 C++ 一致栈）条条命中。选 Widgets 没有悬念。

附带收益：Widgets 走软件渲染，高 DPI 缩放下表格与编辑器的观感更稳定；且**多列表并排 + 锁定滚动**在 Widgets 里就是多个 `QTableView` 共享滚动条位置（`QScrollBar::valueChanged` → `setValue`），几行代码。

### ADR-4 编辑器：QPlainTextEdit + QSyntaxHighlighter + QCompleter

**决定**：普通模式编辑器用 Qt 内置三件套，**零额外依赖**。高级模式（完整 Lua 编辑框）可选引入 QScintilla。

**理由**：

1. **本项目的 DSL 极小**——只有 `$...$` 区段、字面段、helper 名、列表名、字符串。用 `QSyntaxHighlighter` 写几条 `QRegularExpression` 规则就能得到完整的语法高亮，代码量在几百行量级。为一个这么小的语言引入 Monaco / CodeMirror / QScintilla 都不划算。
2. **编辑器的"点击插入列表名"** 用 `QTextCursor::insertText()` 直接实现——这正是构想书里提的需求，在原生控件上是一行代码的事。
3. **`QCompleter` + `QStringListModel`** 提供 helper 名与列表名的自动补全弹出，原生行为。
4. 附带好处：`QPlainTextEdit` 对长文本的性能优于 `QTextEdit`，且天然支持行号栏（`blockCountChanged` + `updateRequest` 是 Qt 官方 Code Editor 示例的标准做法）。

**r1 里的 Monaco → CodeMirror 6 论证作废**，因为整条 WebView 路线已被排除。但原结论「不引入 Monaco」依然成立，且现在有了更强的理由：**根本不需要引入任何第三方编辑器。**

**QScintilla 的定位（可选，不进首版）**：QScintilla 是 Scintilla 的 Qt 移植（Notepad++ 同源），**自带 `QsciLexerLua`**、`QsciAPIs` 自动补全、代码折叠。若高级模式的 Lua 编辑体验不够，它是正确的升级路径。三点注意：
- 许可为 **GPL-3.0**（Riverbank 另售商业授权）——与本项目 GPL-3.0 一致，无冲突。
- **须从源码自行编译**（`qmake && make`），不是一条 `find_package` 能拿到的东西，故不放进首版。
- 它提供的是"更专业的编辑器"，不是"本项目能不能跑起来"的必要条件。

### ADR-5 单运行时，**不采纳「安全级预设不含 Lua」的分级引擎**

（此条沿用 r1，理由未变，且在 C++ 下更加成立——自己写求值器要多写一遍 DSL 语义。）

**背景**：构想书评估建议「预设分两级：安全级（模板 + helper，无任意代码）与高级级（Lua）」。

**决定**：**不实现双引擎**。普通模式与高级模式**统一编译成 Lua、统一走沙箱**。`level` 字段降级为**来源标记**，只用于 UI 警示与加载确认，不改变执行路径。

**理由**：

1. **安全级引擎必然要自己实现求值器**，与构想书已定的「不自己实现执行逻辑」直接矛盾。
2. **双引擎意味着双语义**：同一表达式在两级下行为若有差异，预设被另一级打开就静默变味。
3. **沙箱无论如何都要做**（高级模式需要），做完后安全级引擎就只是冗余——它没有更安全，只是更弱。
4. 预设公开分享时的真实诉求是**来源可见 + 首次加载确认**，这是 UI 问题，不是引擎问题。

**未来升级路径**：若要支持「公开预设市场」，把 Lua 编译为 WASM 执行可获真正强隔离，但会引入体积与性能代价。**本版不做。**

### ADR-6 沙箱：四重限制齐备（C API 实现）

| 限制 | C API 实现 | 要点 |
|---|---|---|
| 能力白名单 | 手工 `luaopen_string/table/math/utf8`，构造 env 表，用 `lua_setupvalue(L, -2, 1)` 挂为该 chunk 的 `_ENV` | 不调 `luaL_openlibs` |
| 指令数 | `lua_sethook(L, h, LUA_MASKCOUNT, N)`，回调里计数并在超限时 `luaL_error` | 钩子由宿主安装 |
| 内存 | `lua_setallocf(L, tracked, ud)`，累计字节数超限时返回 `nullptr` | 触发 `LUA_ERRMEM` |
| 墙钟 | **复用同一个 count 钩子**，`std::chrono::steady_clock` 比对，零额外线程 | 与指令数共用回调 |

**不暴露**：`io`、`os`、`package`、`require`、`load`/`loadstring`、`dofile`、`loadfile`、`debug`、`collectgarbage`、`coroutine`。

**必须处理的三个逃逸面**（纳入实现清单，Phase 2 起即有对抗性测试）：

1. **先分配后检查**：`string.rep`、`string.format("%99999999d")`、`table.concat` 会在限制生效前完成分配。→ 在 env 表里**覆写这几个函数**，先算 `len × n` 规模、超阈值直接报错。
2. **协程重置计数**：`coroutine.yield/resume` 会重置指令计数。→ **不暴露 `coroutine`**。若日后确需，必须在每次 `resume` 后重新安装钩子。
3. **`pcall` 吞掉限制错误**：脚本可 `pcall` 捕获中止错误后继续。→ 限制违规在**宿主侧打独立 flag**（`sandbox::violated()`），每个 protected call 返回后检查，脚本捕获与否都不影响宿主中止整批。

**为什么不用 LuaJIT**：LuaJIT 的 JIT 编译轨迹**不触发 `LUA_MASKCOUNT` 钩子**，指令计数在 JIT 代码中失效——死循环一旦被 JIT 编译就再也拦不住。这与"沙箱必须能终止死循环"的硬约束直接冲突。**必须用 PUC Lua 5.4**（纯解释执行，钩子可靠）。代价是失去 JIT 性能，但本项目 10^5 行规模的字符串拼接远未到需要 JIT 的程度。

### ADR-7 预设格式：TOML ＋ 运行时槽位

（沿用 r1。）

```toml
[preset]
name = "番剧重命名"
version = 1
level = "safe"          # safe | advanced —— 仅作来源标记与 UI 警示，见 ADR-5

[[lists]]
id = "list1"
source = { kind = "dir", path = "${input}", filter = "*.mkv", recursive = false, sort = "natural" }
fill = "ignore"         # empty | ignore | repeat

[[lists]]
id = "list2"
source = { kind = "snapshot", path = "names.txt" }

[output]
mode = "rename"         # rename | argv | stdout
template = "$stem(list1[i])$ $list2[i]$.mkv"

[exec]
jobs = 4
dry_run = true
```

- 给人改的格式（注释、多行字符串），比 JSON 适合"配置一次预设"这个核心形态。
- **预设里不存绝对路径**：`${input}` 等是运行时槽位，由 `--bind input=/path` 或 GUI 拖拽绑定。同时解决「预设可分享」与「路径不该泄漏」。
- 实现：`toml++`（header-only, MIT）。
- 预设可跟随仓库进版本控制，便于分享与回滚。

### ADR-8 列表在 Lua 侧的表示

（沿用 r1。）**决定（v1）**：列表以**普通 Lua 表**注入，值存于 `1..n`，挂 `__index` 元方法函数：越界返回 `""`（不是 `nil`），**不设 `__len`**。

- 值真实存在于 `1..n` → `#list` 天然等于**原始长度**（不含补位）。
- 越界索引时键不存在 → 触发 `__index` → 返回 `""`。
- 不设 `__len` → 缺省（Empty/Repeat/Ignore）是**读取时惰性发生**的，不预填值。

**大列表优化（预留）**：>5 万行时改为 `userdata` 代理（`__index` 直接查 `std::vector<std::string>`，零拷贝）。代价是失去 `table.*` 原生兼容（需 `tolist(l)` 显式转换）。**v1 不做，切换点已预留。**

### ADR-9 `core` 只依赖 QtCore，不做成纯 std 库

**决定**：`core` 用 Qt Core 模块（`QString`、`QDir`、`QFileInfo`、`QProcess`、`QRegularExpression`、`QSettings`、`QSaveFile`），**不使用 QtGui / QtWidgets**。

**理由**：

1. **构想书把「中文路径与编码」明确列为风险。** `QDir`/`QFileInfo`/`QFile` 在 Windows 上走 UTF-16 原生 API，Linux/macOS 走 UTF-8，这套差异 Qt 已经踩平。用 `std::filesystem` + 手工 UTF-8 转换重踩一遍，收益为零、风险不小。
2. **`QProcess` 正好满足执行安全模型的硬要求**：`QProcess::start(program, arguments)` 接收 **argv 数组、不经 shell**，且 Windows 下的参数引号与 Unicode 由 Qt 正确处理。这正是 §4 要的语义，免费拿到。
3. **`QRegularExpression`** 封装 PCRE2 → 正则捕获列表（生成器功能）免费；glob 过滤也能用它统一实现。
4. `QSaveFile` 提供原子写，撤销日志与预设保存直接用。
5. 只依赖 QtCore 保证 `core` 仍是**无界面依赖的库**，单测可 headless 跑（QTest 或 Catch2 皆可）。

**代价**：CLI `bs` 不再是"零依赖单文件"，需随附 `Qt6Core`。这个代价在 §5 量化。

### ADR-10 链接方式：默认动态链接，静态作为可选优化；许可上两者都合法

**决定**：默认走**动态链接 + 平台部署工具**（`windeployqt` / `macdeployqt` / `linuxdeploy`）。静态链接 Qt 作为后期可选优化，不进首版。

**许可结论（关键，且对项目有利）**：

- Qt 6 开源版是 **LGPLv3 / GPLv3** 双许可。Qt 官方明确：**LGPLv3 下静态链接 Qt 会使应用不再是"使用库的作品"，从而触发重新链接义务**（须提供目标文件或源码）。
- 但 **GPLv3 下不存在这个问题**。本项目已经是 **GPL-3.0**（仓库已有 LICENSE），因此**可以按 GPLv3 使用 Qt 并自由静态链接**，义务只剩"整体以 GPL 发布并提供源码"——这本来就是要做的。
- 换言之：**GPL-3.0 这个既有选择，把 Qt 静态链接的许可障碍提前解除了。** 静态与否从此是纯工程问题（自建 Qt 的工作量），不是法律问题。

**这与 QScintilla 一致**：QScintilla 也是 GPL-3.0 / 商业双许可，同样落在这个框架内。

**须记录的连带后果**：选用 Qt-GPLv3 意味着**项目许可被锁定在 GPL 系**。若日后想改为非 GPL 许可，需回头购买 Qt 商业授权（已发布的 GPL 版本无法收回）。这是**一次性单向门**，请知悉后再确认。

**为什么静态不进首版**：自建静态 Qt 需要 `-static` 配置 + 静态 OpenSSL/ICU/harfbuzz/freetype，Windows 下还须 `/MT` 静态 CRT，且**每个平台各做一遍**。这是数天到一周的纯体力活，在功能还没跑通之前做它，性价比为负。

## 3. DSL 规格定稿

本节把构想书末尾「尚待确定的点」逐条裁定。**与语言/UI 选型无关，r1 的结论全部保留。**

### 3.1 编译流程

```
DSL 模板 ──扫描──> [字面段 | 区段] 序列 ──生成──> Lua 源码（编译一次）
                                                    │
                          转成 Lua 函数后逐行调用 ───┘──> 行输出（标量 或 列表）
```

**关键优化：编译一次，产出可复用的 Lua 函数。** 生成的 chunk 形如 `return function(i) ... end`；宿主 `lua_pcall` 一次拿到函数，之后每行只是 `lua_pcall` 该函数。10 万行规模下这是数量级差别。

编译产物（示意，模板 `XX报告书（$i$/$#list1$）`）：

```lua
return function(i)
  return "XX报告书（" .. tostring(i) .. "/" .. tostring(#list1) .. "）"
end
```

### 3.2 求值模型（裁定构想书未决点）

**行循环恒存在。** 批次总行数：

```
rows = 无列表        → 1
     = 有任意 Ignore → min(各列表原始长度)
     = 其余          → max(各列表原始长度)
```

- `i`：当前**宿主行号**（1 起），不因行展开而变化。
- `rows`：**作为变量注入**（不是函数），解决构想书提出的"`$i$` 无从知道边界"。
- 无输入列表时 `rows = 1`，整个模板**自然只求值一次**——构想书"不含行上下文的模板是整体求值一次还是逐行"**不需要特判，模型自己给出答案**。

**行展开规则（裁定构想书 `matrix` 打平后无法逐行展开的冲突）：**

一行内若有**任意区段求值为列表**（长度 n > 1），则该行展开为 n 行；多个区段同时返回列表时取**笛卡尔积**，顺序按区段从左到右（右者为内层循环）。求值为长度 0 的列表 → 该行被跳过。

这条规则同时解决了构想书的两处疑惑：

```text
mv $matrix(list1,list2,'-')$ out        →  9 行，每个组合一条命令 ✔
组合 $i$：$matrix(list1,list2,'-')[i]$   →  索引后为标量，不展开，3 行 ✔
```

构想书担心的"`matrix` 打平之后无法再逐行展开成多元命令"**在这一模型下不成立**——展开发生在"行"这一层，字面段会随展开广播。**无需新增保留结构的 helper，也不破坏"一切皆一维"的约定。**

### 3.3 字符串转义（裁定 `string.format("%q")` 问题）

**不使用 `string.format("%q")`**——它对字面换行会生成真实换行，破坏「一行 DSL 对应一行 Lua」的行号映射。

改用自定义单行转义器：`\` `"` 转义，`\n` `\r` `\t` 转义为转义序列，其余不可打印字符转 `\ddd`，整体包在双引号内。**产物保证单行。**

### 3.4 语法细则

- 区段界定符 `$`。**区段内首个未转义的 `$` 即结束区段**，区段里想写字面 `$` 仍需 `\$`。规则单一、可教学。
- 模板中未配对落单的 `$` **编译报错**（fail loud），不静默当字面量。
- 区段内容只允许**表达式**（不得含语句/赋值）——`level = "safe"` 时编译器强制检查；`advanced` 模式放宽为语句块，允许 `local`、多行、`return`。

### 3.5 helper 集合（v1）

| 类别 | 函数 |
|---|---|
| 列表 | `count(l)` · `index(l,i)` · `tolist(l)` · `slice(l,a,b)` · `concat(l,sep)` · `sort(l)` · `natsort(l)` · `uniq(l)` |
| 组合 | `matrix(a,b,sep)` · `zip(a,b,sep)` |
| 生成 | `seq(from,to,step)` · `seq(n)` · `rand(n)` / `rand(min,max)` · `seed(n)` · `regex(s,pat)` |
| 文本 | `fmt(f,…)` · `upper` · `lower` · `trim` · `replace(s,pat,rep)` · `match(s,pat)` · `pad(s,n,fill)` |
| 路径 | `basename(p)` · `dirname(p)` · `ext(p)` · `stem(p)` · `join(…)` |
| 类型 | `num(s)` · `str(v)` |
| 上下文 | `i`（变量）· `rows`（变量） |

- `index(l,i)` 与 `l[i]` 等价；`count(l)` 与 `#l` 等价——helper 与原生写法并存且结果一致，便于不熟 Lua 的用户迁移。
- **`seed(n)`** 是构想书没提但必需的：`rand` 在多行/并发下若无固定种子，预览与实际执行会不一致，dry-run 的意义就没了。
- 正则相关 helper 底层用 `QRegularExpression`（PCRE2），与 glob 过滤共用一套实现。
- 路径 helper 必须**同时接受 `/` 与 `\`**，输出时按当前平台归一化；但**比较与去重时大小写敏感性随平台**（Windows/macOS 不敏感，Linux 敏感）。

## 4. 执行安全模型

### 4.1 两阶段：plan → apply

```
列表求值 ──> 行输出 ──> [Plan] ──> 冲突检测 ──> diff 呈现 ──> [Apply] ──> 撤销日志
                          │                        │
                     默认停在这里            需 --apply / 点确认
```

- **默认 dry-run。** 没有显式 `--apply`（CLI）或点击确认（GUI），永不产生副作用。
- Plan 是一个**纯数据结构**，可序列化、可 diff、可测试。

### 4.2 三种执行模式

| 模式 | 语义 | 安全要点 |
|---|---|---|
| `rename` | 内置重命名，模板直接给出 `源 → 目标`**路径对**，不做分词 | **不经 shell / 不启进程**，最常用，最安全 |
| `argv` | 外部命令，模板按引号规则分词为 **argv 数组** | `QProcess::start(prog, args)` —— **自带的 argv 语义，不经 `sh -c` / `cmd /c`** |
| `stdout` | 仅输出文本 / 写入剪贴板 / 写文件 | 无副作用 |

**关于"输出为脚本文件"（构想书功能）**：**不生成 `.ps1` / `.bat`**——非 ASCII 路径在这些格式下会因编码损坏（构想书评估已点出）。改为**输出 argv 清单（JSON）**，需要时由运行器解释执行，中文路径全程走 UTF-8。

### 4.3 重命名冲突检测（apply 前强制）

| 检查 | 处理 |
|---|---|
| 源不存在 | 报错并跳过 |
| 两个输出同名 | 报错，整批拒绝（避免静默覆盖） |
| 目标已存在（且非本次批内源文件） | 警告 + 默认中止 |
| **批内互换**（a→b 且 b→c，或 a↔b） | 自动**两阶段重命名**：全部先改为临时名，再改为终名 |
| 仅大小写不同的重命名 | **在 Windows/macOS 上走临时名**（大小写不敏感文件系统） |
| 路径穿越（目标逃出绑定根目录） | 默认拒绝，可显式放开 |

### 4.4 文件行绑定路径而非序号

构想书评估点出：「文件行必须绑定路径而不是序号，否则目录变动后序号错位，命令会打到别的文件上」。

**落实方式**：`dir` 类型列表在**求值那一刻**把 `(行号 → 绝对路径)` 快照进 Plan。apply 阶段校验该路径仍存在且未被修改（比对 mtime/size），不一致则该行标红并要求重新生成 Plan。**绝不按序号回查目录。**

### 4.5 撤销

- 每次 apply 写一份 JSONL 日志（`src`、`dst`、`ok`、`ts`、`mode`）。
- `bs undo <journal>` 逆序回放，并同样做冲突检测（目标名是否已被占用）。
- 位置：`QStandardPaths::AppDataLocation`（Windows `%LOCALAPPDATA%\BatchSmith\`，Linux `~/.local/share/BatchSmith/`，macOS `~/Library/Application Support/BatchSmith/`）。
- 写入用 `QSaveFile` 保证原子性。

### 4.6 自然排序

列表默认排序必须支持自然排序，否则 `file10` 会排在 `file2` 之前。**这一条影响正确性，不是体验问题。** 自实现分块比较（数字段按数值比、其余按 `QString::localeAwareCompare`），中文文件名排序才不会错乱。

### 4.7 并发

- `exec.jobs` 控制并行度，默认 `min(4, QThread::idealThreadCount())`。
- **Plan 阶段串行**（冲突检测需要全局视图），**Apply 阶段并行**。
- 重命名因涉及临时名交换，**同批内串行**；`argv` 模式可安全并行。
- 实现用 Qt Concurrent 或 `QThreadPool`；`core` 的接口层（`ICommandRunner`）需保证线程安全。

## 5. 多平台与轻量化落实

### 5.1 目标产物（数字已实测，P4 阶段在 Windows/MinGW 上量得）

实测环境：Windows + MinGW 11.2 + Qt 6.7.2 + `windeployqt`，Release 构建。

| 产物 | 形态 | **实测** | 说明 |
|---|---|---|---|
| GUI 发布目录（`windeployqt` 默认） | 动态链接 | **56.2 MB / 50 个文件** | 大头是 `opengl32sw.dll` 19.7MB、`Qt6Gui` 9.8MB、`Qt6Core` 6.5MB、`Qt6Widgets` 6.4MB、translations 4.8MB、`D3Dcompiler_47` 4.0MB |
| GUI 发布目录（精简） | 动态链接 | **27.8 MB / 18 个文件** | 加 `--no-translations --no-opengl-sw --no-system-d3d-compiler --no-compiler-runtime` |
| **GUI 安装包（压缩后）** | zip/LZMA2 | **11.7 MB** | 上述精简目录压缩所得；LZMA2 安装包通常与此接近 |
| GUI 单文件 | 静态链接（需自建静态 Qt） | 未实测 | 不进首版，见 ADR-10 |
| `bs`（CLI）可执行文件 | Release | **0.06 MB** | Lua 以静态库形式链接，但 Phase 2 之前无代码引用它，链接器不会拉入任何 Lua 目标文件 |
| GUI 可执行文件 | Release | **0.10 MB** | 同上 |

体积构成的关键结论：

1. **`opengl32sw.dll`（19.7MB）是单笔最大开销**，而 Qt Widgets 根本不走 OpenGL。`--no-opengl-sw` 一刀砍掉 35%。这是"轻量化"最有效的一步。
2. **translations（4.8MB）** 默认全量拷贝，`--no-translations` 直接省掉。
3. `windeployqt` 还会带 **`Qt6Network.dll` + tls/networkinformation 插件约 2–3MB**，而本项目不用网络。可以再删，但**必须逐个验证**——删错插件是静默失败，比多几 MB 代价大得多（见 §5.4 第 3 条）。
4. Phase 2 接入 Lua 后 `bs.exe` 会增长约 0.3–0.5MB（Lua 5.4 静态编译后的实际体积），届时再回填。

**修正 r1 与 r2 早前的表述**：r1 说「C++/Qt 产物体积约为 Rust 方案的 3–5 倍」，只对静态自建 Qt 成立；r2 估的「安装包 15–25MB」偏保守。**实测是 11.7MB**，与 Tauri 方案的 8–15MB 基本同一量级。

### 5.2 「轻量化」的重新界定

Qt 方案**达不到**「3–6MB 单文件」；但它**达到**了这些更实质的点：

| 目标 | Qt 方案是否满足 |
|---|---|
| 不打包 Chromium / 不依赖 JVM / .NET / Python | ✅ 只随附 Qt 自身 DLL（18 个文件） |
| 启动快 | ✅ Qt Widgets 冷启动通常 100–300ms |
| 内存占用可控 | ✅ Widgets 软件渲染，比 WebView 方案低 |
| 安装包可接受 | ✅ **实测 11.7MB**（精简 + 压缩） |
| 极致单文件 | ❌ 需自建静态 Qt（ADR-10，可选后补） |

**判断**：构想书语境下的"轻量化"真正反对的是"为了一个批量改名工具塞进一整个浏览器引擎"。Qt 动态部署满足这个意图。若"单文件"确实是硬需求，静态 Qt 是明确的补救路径且**许可上已经合法**。

### 5.3 构建矩阵

- Windows：MSVC x64 + arm64（`windeployqt`）
- macOS：`CMAKE_OSX_ARCHITECTURES="x86_64;arm64"` 出 universal（`macdeployqt`）
- Linux：`linuxdeploy` + AppImage

CI（GitHub Actions）一次性出全部产物与 SHA256。**注意：macOS 产物必须在 macOS 上构建，三平台都需要真机验证**（Windows 上开发完直接编其他平台是 Qt 项目的经典翻车点）。

### 5.4 轻量化的具体手段清单

1. **无 Chromium、无 JVM、无 .NET、无 Python 运行时。**
2. Release 构建 + `--no-translations` + `--no-compiler-runtime`（视目标机环境）。
3. 剔除确定不用的插件（如 `imageformats/qjpeg.dll`）——但要逐个验证，删错会静默失败。
4. `CMAKE_INTERPROCEDURAL_OPTIMIZATION`（LTO）开启；`-Os` 对体积敏感处可用。
5. 静态链接 Qt（可选阶段）：GPL-3.0 下合法，须自建 Qt。
6. 不用 `Qt5Compat`、不用 Qt Quick、不用 Qt WebEngine。**只链接 `Qt6::Core` / `Qt6::Gui` / `Qt6::Widgets`**。
7. 表格用 `QTableView` 原生虚拟滚动，10 万行也只渲染视口内的行——**这是原生方案相对 WebView 方案的实质优势**，WebView 里得靠 `@tanstack/virtual` 之类自己实现。

## 8. 风险登记表

| 风险 | 等级 | 缓解 |
|---|---|---|
| 沙箱逃逸（死循环/内存炸弹/`pcall` 吞错/协程重置） | 高 | ADR-6 四重限制 + 三个逃逸面针对性处理；Phase 2 起即有对抗性测试；**不用 LuaJIT** |
| 执行不可逆造成数据损失 | 高 | 默认 dry-run；`QProcess` argv 不经 shell；冲突检测；两阶段重命名；撤销日志 |
| 序号错位导致命令打到别的文件 | 高 | §4.4 行绑定绝对路径 + apply 前 mtime 校验 |
| 中文路径在"输出脚本"下编码损坏 | 中 | 不生成 `.ps1`/`.bat`，改为 argv JSON 清单（§4.2）；路径处理全部走 `QDir`/`QFileInfo` |
| 三平台未真机验证导致布局/API 翻车 | 中 | CI 三平台矩阵 + 每平台人工冒烟；**禁止只在 Windows 开发后直接编其他平台** |
| macOS 分发需签名与公证 | 中 | 首版可先只出未签名包自用；公开分发时再补签名流程 |
| 静态 Qt 自建的体力成本 | 中 | ADR-10：**不进首版**，仅在"单文件"成为硬需求时启动 |
| 范围蔓延（列表源与生成器无限扩） | 中 | Phase 4 判断门槛；不过就不启动 Phase 5 之后 |
| 项目许可被锁在 GPL 系 | 中 | ADR-10 已记录为单向门；若日后要闭源只有买商业 Qt 一条路 |
| CLI 与 GUI 结果不一致 | 中 | 逻辑全在 `core`；Phase 6 验收明确要求 Plan 逐字节一致 |
| `matrix` 笛卡尔积行数爆炸 | 低 | Plan 阶段统计展开后总行数，超阈值（如 100 万行）时警告 |

## 9. 待拍板项

### 已确认

| 项 | 结论 | 依据 |
|---|---|---|
| 语言与 GUI 框架 | **C++20 + Qt 6 Widgets** | 用户明确倾向 native 控件 |
| 依赖管理方式 | **git submodule** | 用户要求不让第三方代码污染自己的仓库 |
| 取消"安全级/高级级"双引擎（ADR-5） | 已确认 | 用户批准方案 |
| ADR-10 的单向门（项目锁在 GPL 系） | 已接受 | 仓库既已是 GPL-3.0 |
| **「轻量化」是否达标** | **已达标**：实测安装包 **11.45 MB** | 见 §5.1，比原估的 15–25 MB 更好 |

### 仍未定

1. **GUI 编辑器用哪一档**（ADR-4）：首版只用 Qt 内置的
   `QPlainTextEdit` + `QSyntaxHighlighter` + `QCompleter`，还是高级模式直接上 QScintilla？
   —— **推迟到 Phase 6 再定**，那时有真实的高亮/补全需求可参照。
2. **是否要把静态 Qt 提前**（ADR-10 / Phase 8）：只有"单文件分发"成为硬需求时才值得。
   当前 11.45 MB 的 zip + 免安装目录已能满足自用。
3. **判断门槛的量化标准**（Phase 4）："一周内每天在用"是构想书原话，但"在用"如何计数
   （启动次数？实际 apply 成功的批次数？）到 Phase 4 收尾时再定。

## 附 A：与构想书「尚待确定的点」的对照
